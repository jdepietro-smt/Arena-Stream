# Arena Portal

Web side of Arena Link, added next to the existing server services (nothing is replaced):

- **Web links.** Share a live stream as a link that plays in any browser, with an expiry and an optional password. Links can be revoked at any time, and each open is logged.
- **Wall.** A multiview of every stream on air, one picture per tile (the same thumbnails as the Streams tab, refreshed every few seconds), with its name, state, video rate (received versus announced) and web viewers. A green border is healthy, amber is a low rate, red is a problem; a stream that left in the last 24 hours stays on the wall as a red OFF AIR tile instead of vanishing. Problems sort first. Choose how many tiles across, filter by name, and use Full screen for a monitor on the wall. Click a tile for live video (same limit of live previews as elsewhere). H.265 streams show no picture, as in the Streams tab. Uses the monitoring data, so alerts need the monitor running.
- **Streams.** Live encoders from the directory: format, codec, bitrate, web viewers, links.
- **Previews.** A thumbnail per stream (and per decoder, showing what it plays) on the Streams and Decoders tabs; click one for live video. Live previews are limited to three at a time because each sends the full stream to the browser.
- **Decoders.** See every decoder PC running the Arena Link app and choose which stream each one plays out to SDI.

## Admin section (owner only)

The Admin tab is for Admin accounts. Anyone else (a User account, or the shared password) has to give a second, owner-only password, and that unlock lasts 15 idle minutes (it slides while you work). It holds:

- **Account and security.** Change the everyday portal password and the owner password (both need the current owner password; either change, and "Sign out everywhere", signs every browser out). Recent sign-ins and failed attempts.
- **Settings.** Link address, relay delay for web viewers, live previews at once, thumbnails on or off and how often, default link expiry, and whether every link needs a password. They apply at once, no restart; a new relay delay is pushed to the mediamtx paths already in use.
- **Server health.** State of mediamtx, the relay, the directory, the share-link check, the portal, Comms, LiveKit and nginx; load, memory, disk (`/` and `/var/recordings`); directory and mediamtx reachability; web viewers. A Restart button per service (with a warning for the ones that carry streams).
- **Monitoring and alerts.** Checks the whole system every 5 seconds and keeps 24 hours of history per stream (video rate each minute, share of time on air). Open alerts show at the top of the Monitoring page: a stream off air (15 s), a video rate under half of what the encoder announces (the server measures what it really receives), a decoder gone quiet, a stopped service, a disk over 90% (critical at 97%), an overloaded server or low memory, and the directory being unreachable. Each alert opens and clears by itself and is logged. Under Send alerts to, paste a Slack, Teams or generic webhook address to be told when one opens and when it clears; Send a test alert checks it reaches you. Thresholds are in `lib/monitor.js`.
- **Backup directory.** The Link directory is what lets decoders see what is on air. Install a second one on another server with `LINK_KEY='<main key>' LINK_RELAY_SECRET='<relay passphrase>' bash link/directory/install.sh` (both values are in `/etc/arena-link.env` on the main server), then put both addresses in each Link app's Settings (Directory address, `http://main:8002,http://backup:8002`). Encoders announce to both; decoders, heartbeats and updates use whichever answers, main first. Enter the backup's address under Monitoring → Backup directory to have it watched: you are alerted if it stops answering, or if a stream is not announcing to it (an old app, or one without the backup address). The directory holds only live announcements, so nothing needs syncing; remote control commands and the update release files live on the main one only (update files can be copied to the backup's `/var/lib/arena-updates` if you want updates to keep flowing during an outage). The portal, web links and Comms are not duplicated by this.
- **Software updates.** Admin → Software updates publishes new builds of the Arena Link app to every PC. **To release:** raise `version` in `ui/link-app/package.json`, run `npm run build` there, then upload `release/Arena-Link-Setup-<version>.exe` on that page (the file name carries the version, so keep it as the build made it). A new upload is **held back**: nothing happens until you choose Release to chosen PCs first (a canary group) or Release to everyone. Each app asks the directory every ten minutes, downloads in the background (resumable, checked against the published size and SHA-256 before it is ever run), and installs when nothing is live on that PC and it has been quiet two minutes, or inside a maintenance window set in the app's Settings; a PC can also be set to wait for a click or to never update. It stops its streams, runs the installer silently and starts again. The PCs table shows each PC's version and update state (downloading, waiting, installing, problem). Roll back to a kept version makes PCs move to exactly it (also held until released); the last five versions are kept. A PC running an app from before this feature must be updated by hand once. Files live in `/var/lib/arena-updates` (made by `portal/deploy/install.sh`; the directory serves them). An update installer that needs administrator rights will show a Windows prompt on a PC that is not set up to allow it.
- **Path health.** Each encoder PC reports, for every stream, which relays it publishes to (connected or not, round trip, how much had to be re-sent, packet loss protection setting); each decoder reports whether it is reading one relay, two, or the encoder directly on the LAN, and the health of each path. Monitoring shows them as chips next to each stream and decoder, the Wall shows `relays 1/2` on each tile, and these raise alerts: a stream not reaching any relay (critical), running without its backup relay (warning, after 20 s), a lossy link to the relay (5% or more re-sent for 30 s, with advice to turn on packet loss protection), and a decoder that is set to use two relays but has lost one. Needs the updated Link app and directory.
- **Encoder control and schedules.** Admin → Encoder control lists every encoder PC running the Arena Link app and its streams (state, bitrate), with Start, Stop, Restart and a bitrate box for each. The PC reports to the directory every 4 seconds and picks up commands from it, carries them out exactly as a click in the app would, and reports back; the page shows the answer (done, or why not, such as no signal). Schedules start and optionally stop a stream at set times, once on a date or on chosen weekdays, in the time zone set under Settings (daylight saving is handled). A start missed by more than ten minutes (portal down) is skipped rather than run late. If a PC fails a scheduled command or does not answer within a minute, an alert is raised and sent to the webhook. A stop from here or from a schedule is expected: the stream shows as STOPPED on the Wall and does not raise an off-air alert. The Link app has a setting (Connection) to refuse remote control per PC; commands older than two minutes are ignored by the app. Needs the updated directory (`bash portal/deploy/install.sh` updates it) and an Arena Link app that includes remote control.
- **Capacity test.** Finds how many 10 Mbps streams the server carries, from the server itself (so this site's internet connection is not the limit). `captest.js` makes a 20 s, 10 Mbps sample once, publishes N copies to the relay over loopback as `CT-1`..`CT-N`, and reads each back twice: over SRT through the relay like a decoder PC, and through a mediamtx path (RTSP) like a browser viewer. N ramps by a step; every second it samples system CPU, the load of the test generator (reported separately, so it can be left out), memory, network and the busiest processes. The page shows live tiles and a per-step table with a verdict. It stops by itself when CPU stays above a limit (default 90% for 8 s), free memory drops below 1 GB, readers fall behind or stall, or a live stream is affected; a Stop button and a 25 minute hard limit also apply. It refuses to start while live streams are on air unless you allow it. The result gives the server-side CPU per stream (a least-squares fit over the clean steps) and the stream count at 70% of all cores. WebRTC viewers are real: a second mediamtx (the viewer host, our own child process on ports 19997/18554, its CPU counted with the generator) pulls each stream from the real mediamtx over WHEP, so the real one does the encryption work; if mediamtx is too old for WHEP sources or WebRTC cannot reach itself, the viewers are left out and the result says so. Viewer traffic runs over loopback, so the network columns do not include it; budget about 10 Mbps out per viewer. The load stop is 2.5 times the core count. The synthetic streams are not announced to the directory, so decoders and the Streams tab never see them. The runner starts through the root helper as its own transient service (`arena-captest`, low priority, 2 GB memory limit), so the portal's CPU limit does not hold it back. Before ramping it checks that `ffmpeg` has SRT and that one stream goes through the relay and back; if not, the page says exactly why (the relay secret is redacted from any error text). Readers are counted from the bytes they actually receive (through a pipe), and a publisher or reader that dies before data flows is restarted a few times. By hand: `node /opt/arena-portal/captest.js --streams 20 --step 2`, or just the check: `node /opt/arena-portal/captest.js --preflight` (with the portal's environment: `set -a; . /etc/arena-portal/env; set +a`).
- **Comms (the intercom server).** The top bar has four sections: Video (Streams, Web links, Decoders), Comms, Remote access (reserved, empty for now) and Admin. Comms is its own section, not part of Admin; it needs the same owner access (an Admin account has it already). It controls the Arena Comms server: who is online (with Kick), groups and what each may do per channel (Talk, Listen, and Music on music channels), people and their groups, and disabling a login. Only controls and permissions go through the portal; audio stays on the Comms server. It uses Comms' own admin API (`/admin/api/`), so Comms itself needs no change. Connect once: enter the Comms address (for example `https://5.161.235.143/comms`), press Check the server, compare the certificate fingerprint with the one on the Comms server and tick that you trust it, then enter a Comms administrator login. The connection is pinned to exactly that certificate (a different or forged one is refused; the hostname is not checked because the certificate is for an IP address). The Comms admin password is stored sealed (AES-256-GCM, key from the portal secret) in `admin.json` and never sent to the browser. Linked accounts: the Portal accounts and Comms logins card on the Comms page links a portal account to a Comms login. The Comms login has the same username, takes its display name from the profile, and gets the same password whenever you set one in the portal (the portal never stores the plain password; it passes it on at that moment). Unlinking or deleting a portal user only disables the Comms login, never deletes it. A portal Admin is not made a Comms administrator, and this page cannot change Comms administrator flags or other people's passwords. If Comms is unreachable a portal change still happens and the page says the Comms side was not updated. Every change is in the activity log (`comms.*`).
- **Activity and links.** Every sign-in, link created, revoked or opened (with the viewer's address), decoder change, setting change and restart, filterable; and all links with views, distinct viewers and last view.

Restarts: the portal runs as an unprivileged user, so it leaves the service name in `/var/lib/arena-portal/ctl/request`; `arena-portal-ctl.path` runs `ctl.sh` as root, which restarts it only if the name is on a fixed list. Settings, the passwords (hashed with scrypt), the session epoch and the activity log live in `/var/lib/arena-portal/admin.json`.

- **Portal users.** Named accounts, each with its own username and password (letters in any case; at least 10 characters), added, re-passworded, given a role and deleted from Account and security. A role is **Admin** or **User**. An Admin account opens this Admin area straight away, with no second password. A User account, and anyone using the shared portal password, can use the rest of the portal and must give the owner password to open this area. Accounts saved before roles existed count as Admin. Changing a password or deleting an account signs that person out; an Admin account changes passwords with its own password. The shared portal password keeps working until you turn it off (it cannot be turned off while there are no accounts, or when it would remove the last one). Sign-ins and opens in the activity log carry the username. **Profiles:** each account can have a full name and an email address (both optional; the email must look like one). An Admin sets them for anyone with Edit profile, or when adding the account; each signed-in account edits its own by clicking its name (shown top right instead of the username) in the page header. `add-user.js` takes `--name` and `--email`.

Accounts from the server, with no typing of passwords: `node /opt/arena-portal/add-user.js <username>` creates an Admin account (`--role user` for a plain user) with a generated lowercase password it prints once (an existing account is left alone; `--reset` gives a new password). `bash portal/deploy/install.sh <username>` does the same as part of an install or update. Both stop the portal for a moment, because it holds its data in memory.

Lost the owner password? On the server: `node /opt/arena-portal/reset-owner.js` prints a new one, signs everyone out and turns shared sign-in back on.

## How a web link plays

```
encoder --SRT--> relay :8895 --SRT (read)--> mediamtx (path portal_<name>_<tag>, on demand)
                                                 |  WebRTC (WHEP), proxied by the portal
                                                 v
browser  <--- /w/<link id>  (portal checks: link active, not expired, password)
```

The portal creates the mediamtx path on first use and mediamtx closes it 15 s after the last viewer leaves. The browser talks to the portal, never to mediamtx directly; the media path name carries a secret tag so it cannot be guessed. Expect roughly 150 to 300 ms more delay than the SDI path.

Thumbnails: while the admin page is open, the portal runs one `ffmpeg` per stream that reads the SRT relay, decodes key frames only, and writes a 480 px JPEG every few seconds (`lib/thumbs.js`). A worker stops about 25 s after the page stops asking. It needs an `ffmpeg` with SRT support (the Ubuntu package has it; the installer checks). The first picture appears after the first key frame, typically within 10 s.

Browser limits: H.265 streams cannot be played (the portal says so and the Streams tab flags them); use H.264 in the encoder. Interlaced H.264 plays but depends on the browser's decoder.

## Remote decoder control

The Arena Link app (decoder side) sends a heartbeat to the directory every 4 s. The portal asks the directory to tell a decoder to play a stream; the app applies it like a click and saves it as the decoder's stream. The first reply after the app starts is only recorded, so an old request is never replayed. Requests for an offline decoder are kept for 10 minutes. Directory calls:

| Call | Purpose |
|---|---|
| `POST /v1/decoder/heartbeat` | decoder reports `{id, name, host, state, stream}`; reply holds the pending `want` |
| `POST /v1/decoder/want` | `{id, stream}`; `""` disconnects |
| `GET /v1/decoders` | decoders seen in the last 20 s |

## Install on the server

```
cd /opt/arena-stream; git pull; bash portal/deploy/install.sh
```

It updates the directory (adds the decoder calls; the access key is kept), installs the `arena-portal` service on `127.0.0.1:8910`, and adds `/portal/` and `/w/` to the nginx sites that serve the dashboard (backups kept as `*.pre-portal`, rolled back on any nginx error). It prints the portal address and the admin password. Re-running keeps the password, secret and links.

- Admin: `https://<server>/portal/` (https only; plain http is redirected).
- Links: `http://<server>/w/<id>` by default, so viewers do not get a certificate warning. Set `PORTAL_PUBLIC_BASE` in `/etc/arena-portal/env` (for example to `https://stream.example.com`) once there is a domain, then `systemctl restart arena-portal`.
- Open TCP 80 and 443 in the Hetzner Cloud firewall. Browser WebRTC media uses mediamtx's existing UDP 8889.

Settings live in `/etc/arena-portal/env`; links and the view log in `/var/lib/arena-portal/portal.json`.
